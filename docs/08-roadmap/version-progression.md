نسخهٔ پروژه با ساختار `MAJOR.MINOR.PATCH` و بر اساس **لایه‌بندی موتورها** در `DEPENDENCIES.md` تعیین می‌شود:


## قواعد افزایش (گام‌به‌گام از راست به چپ) 🔒

### قاعدهٔ ۱ — هر فاز = +1 به PATCH
🔒 با پیاده‌سازی هر فاز، رقم سمت راست (PATCH) یک واحد افزایش می‌یابد.

```
0.0.0 → (M1) → 0.0.1 → (M2) → 0.0.2 → ...
```

### قاعدهٔ ۲ — انتقال لایه = carry به MINOR
🔒 وقتی لایهٔ N کامل شد و لایهٔ N+1 شروع می‌شود:
- MINOR یک واحد افزایش می‌یابد
- PATCH به 0 بازمی‌گردد

```
0.0.2 (آخرین فاز L0) → 0.1.0 (شروع L1) → 0.1.1 (اولین فاز L1) → ...
```

### قاعدهٔ ۳ — بدون پرش از 0.0.10 به 1.0.0 🔒
🔒 نسخه‌ها باید **گام‌به‌گام از راست به چپ** افزایش یابند:
- PATCH: 1 → 2 → ... → 9
- وقتی PATCH به 9 رسید و لایه کامل نشد، **نه** 0.0.10، بلکه:
  - اگر لایهٔ بعدی وجود دارد → carry به MINOR (مثلاً 0.0.9 → 0.1.0)
  - هر لایه حداکثر 9 فاز دارد (طراحی شده برای جلوگیری از سرریز)

### قاعدهٔ ۴ — انتشار نهایی = carry به MAJOR
🔒 وقتی همهٔ لایه‌ها (L0-L6) و اپلیکیشن‌ها (0.7-0.9) کامل شدند:
- MINOR سرریز می‌کند (9 → 10)
- MAJOR یک واحد افزایش می‌یابد (0 → 1)
- MINOR و PATCH به 0 بازمی‌گردند

```
0.9.5 (آخرین فاز Apps-Prof) → 1.0.0 (Release)
```

### قاعدهٔ ۵ — عبور از همهٔ MINORها
🔒 برای رسیدن به 1.0.0، پروژه باید از **تمام** نسخه‌های MINOR (0.1.0, 0.2.0, ..., 0.9.0) عبور کند. هیچ نسخه‌ای پرش نمی‌کند.

## چرا این طرح از کد اسپاگتی جلوگیری می‌کند؟

۱. **هر لایه فقط به لایه‌های قبلی وابسته است** — وابستگی به لایهٔ هم‌زمان یا آینده ممنوع.
۲. **هر فاز کوچک است** (۱-۵ موتور) — قابل مدیریت در ۱-۲ هفته.
۳. **نسخه نشان‌دهندهٔ پیشرفت واقعی است** — نسخه 0.3.5 یعنی لایهٔ ۳ کامل شده تا فاز ۵.
۴. **انتقال لایه = نسخهٔ پایه** — وقتی نسخه 0.4.0 می‌بینیم، می‌دانیم L4 شروع شده.
۵. **Release 1.0.0 فقط پس از عبور از همهٔ لایه‌ها** — هیچ میان‌بر وجود ندارد.
